# Матрица трассировки требований ЛР1 и модели/API ЛР2

## 1. Матрица трёх критериев приёмки

| Требование ЛР1 | Поле или сущность модели | Запрос API | Критерий приёмки |
|---|---|---|---|
| Сотрудник отдела снабжения создаёт заявку, указывая заголовок, материал и описание. Сервер присваивает номер и статус `New`. | `PurchaseRequest`; `title`; `materialId` (FK на `NomenclatureItem`); `description`; серверные `id`, `number`, `status`; `authorId` | `POST /api/purchase-requests` | Критерий 1 — создать объект |
| Сотрудник отдела снабжения или руководитель назначает специалиста. После назначения статус остаётся `New`. | `PurchaseRequest.assigneeId` (FK на `AppUser`), `PurchaseRequest.status`; пользователь-исполнитель имеет роль специалиста по закупкам | `PATCH /api/purchase-requests/{id}/assignee` | Критерий 2 — назначить исполнителя |
| Назначенный специалист переводит свою заявку из `New` в `InProgress`; другой пользователь не может выполнить этот переход. | `PurchaseRequest.status`; `PurchaseRequest.assigneeId`; `AppUser.id` и права пользователя | `PATCH /api/purchase-requests/{id}/status` | Критерий 3 — исполнитель перевёл в работу |

## 2. Проверка полноты

- Для создания заявки в модели есть заголовок, ссылка на материал и описание.
- `id`, `number` и `status` устанавливаются сервером, а не клиентом.
- Для назначения исполнителя предусмотрено отдельное поле `assigneeId`, которое допускает `NULL` до назначения.
- Назначение исполнителя и изменение статуса выполняются разными запросами.
- Право менять статус связано с назначенным пользователем: специалист может перевести в работу только назначенную ему заявку.
- Все четыре статуса определены в модели: `New`, `InProgress`, `Closed`, `Cancelled`.

## 3. Связь с функциональными требованиями ЛР1

| Требования ЛР1 | Как отражены в ЛР2 |
|---|---|
| ФТ-1, ФТ-2, ФТ-3 | Поля `title`, `materialId`, `description`, проверка материала и ограничений длины при `POST` |
| ФТ-4, ФТ-5, ФТ-6 | Поле `assigneeId`, отдельный PATCH назначения, запрет менять статус при назначении |
| ФТ-7, ФТ-8, ФТ-9, ФТ-10 | Поле `status`, разрешённые переходы, отдельный PATCH статуса, проверка назначенного пользователя |
| ФТ-11 | Серверная проверка роли и запрет создания заявки специалистом |
| ФТ-12 | `GET /api/purchase-requests`, DTO списка с номером, заголовком, материалом, исполнителем и статусом |

## 4. Вывод

Все три обязательных критерия приёмки ЛР1 связаны с конкретными полями модели данных и отдельными запросами API. Модель позволяет создать заявку без исполнителя, назначить специалиста без автоматической смены статуса и отдельно перевести назначенную заявку в работу с серверной проверкой прав.
