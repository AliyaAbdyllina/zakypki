## 1. Три критерия приёмки

| Требование | Поле или сущность | Запрос | Критерий |
|---|---|---|---|
| Создать объект | `PurchaseRequest`: `title`, `materialId`, `description`, `id`, `number`, `status` | `POST /api/purchase-requests` | 1 |
| Назначить исполнителя | `PurchaseRequest.assigneeUserId` → `User.id` | `PATCH /api/purchase-requests/{id}/assignee` | 2 |
| Исполнитель перевёл в работу | `PurchaseRequest.status`, `assigneeUserId` | `PATCH /api/purchase-requests/{id}/status` | 3 |

### Критерий 1. Создать объект

> **Дано:** сотрудник отдела снабжения вошёл в систему.
>
> **Когда:** он заполняет заголовок от 5 до 80 символов, указывает ссылку на материал числом больше 0, вводит описание от 10 до 500 символов и нажимает «Создать».
>
> **Тогда:** появляется заявка со статусом `New` («Новая») и человеческим номером.

**Как обеспечивается.** Запрос передаёт `title`, `materialId` и `description`, сервер проверяет их границы и возвращает `201`. Значения `id`, `number` и `status: "New"` сервер задаёт сам, поэтому клиент не может их подменить. Роль проверяется по `User.role`.

### Критерий 2. Назначить исполнителя

> **Дано:** сотрудник отдела снабжения вошёл в систему и существует заявка со статусом `New`.
>
> **Когда:** сотрудник отдельным действием назначает специалиста по закупкам.
>
> **Тогда:** у заявки появляется назначенный исполнитель, при этом статус заявки не изменяется автоматически и может оставаться `New`.

**Как обеспечивается.** Назначение — отдельный запрос с единственным полем `assigneeUserId`. Он записывает внешний ключ на `User` и не затрагивает `status`.

### Критерий 3. Исполнитель перевёл в работу

> **Дано:** назначенный специалист по закупкам вошёл в систему.
>
> **Когда:** он переводит назначенную ему заявку со статусом `New` в `InProgress`.
>
> **Тогда:** заявка получает статус «В работе», а пользователь с другим логином не может перевести эту заявку в работу.

**Как обеспечивается.** Запрос передаёт `{ "status": "InProgress" }`. Сервер сравнивает `assigneeUserId` с вошедшим пользователем: совпадение даёт `200`, чужая заявка — `403`, отсутствие исполнителя — `409`.

## 2. Функциональные требования

Эта таблица подтверждает, что для каждого требования есть место в модели и API. Запросы `GET /api/materials` и `GET /api/users?role=PurchasingSpecialist` вспомогательные и не входят в обязательный минимум методички. Правила, которых нет в ЛР1 , отмечены как проектные решения в [`data-model.md`](data-model.md) и [`api-contract.md`](api-contract.md).

| Требование | Поле или сущность | Запрос |
|---|---|---|
| ФТ-1. Создание заявки | `PurchaseRequest` | `POST /api/purchase-requests` |
| ФТ-2. Проверка полей | `title`, `materialId`, `description` | `POST /api/purchase-requests` → `400` |
| ФТ-3. Выбор материала | `Material.id`, `Material.name` | `GET /api/materials` |
| ФТ-4. Назначение сотрудником | `assigneeUserId` | `GET /api/users?role=PurchasingSpecialist`, `PATCH …/assignee` |
| ФТ-5. Назначение руководителем | `assigneeUserId` | `GET /api/users?role=PurchasingSpecialist`, `PATCH …/assignee` |
| ФТ-6. Назначение не меняет статус | `assigneeUserId`, `status` | `PATCH …/assignee` |
| ФТ-7. `New` → `InProgress` | `status` | `PATCH …/status` |
| ФТ-8. `InProgress` → `Closed` | `status` | `PATCH …/status` |
| ФТ-9. Отмена своей заявки | `status` | `PATCH …/status` |
| ФТ-10. Запрет на чужую заявку | `assigneeUserId`, `status` | `PATCH …/status` → `403` |
| ФТ-11. Специалист не создаёт | `User.role` | `POST /api/purchase-requests` → `403` |
| ФТ-12. Список заявок | `number`, `title`, `materialId`, `assigneeUserId`, `status` | `GET /api/purchase-requests` |
