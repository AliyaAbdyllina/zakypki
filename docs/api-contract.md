**Это договор о будущем API, а не описание готового сервера.** Реализация запланирована на следующие лабораторные работы.

Базовый адрес: `http://localhost:5000`. Формат данных: JSON.

**Значения в примерах демонстрационные:** идентификаторы, номера заявок, названия материалов, имена, тексты заявок и даты не являются утверждёнными справочными данными.

## 1. Сводная таблица

### 1.1. Обязательные запросы ЛР2

| Метод и путь | Назначение | Тело запроса | Успех | Возможные ошибки |
|---|---|---|---|---|
| `GET /api/purchase-requests` | список заявок | — | `200`, массив или `[]` | `401` |
| `GET /api/purchase-requests/{id}` | одна заявка | — | `200`, объект | `401`, `403`, `404` |
| `POST /api/purchase-requests` | создать заявку | `title`, `materialId`, `description` | `201`, объект | `400`, `401`, `403`, `409` |
| `PATCH /api/purchase-requests/{id}/assignee` | назначить исполнителя | `assigneeUserId` | `200`, объект | `400`, `401`, `403`, `404`, `409` |

### 1.2. Вспомогательные запросы

Не входят в обязательный минимум методички. Это проектное решение: запросы нужны, чтобы формы могли показать варианты выбора.

| Метод и путь | Назначение | Основание | Успех | Ошибки |
|---|---|---|---|---|
| `GET /api/materials` | справочник материалов | ФТ-3 | `200`, массив или `[]` | `401` |
| `GET /api/users?role=PurchasingSpecialist` | специалисты для назначения | ФТ-4, ФТ-5 | `200`, массив или `[]` | `400`, `401`, `403` |

Запрос входа в контракт пока не включён: его форма зависит от выбора между cookie и JWT в ЛР11.

## 2. Коды ответов

| Код | Когда |
|---|---|
| `200` | данные прочитаны или действие выполнено; пустой список — тоже `200` и `[]` |
| `201` | заявка создана |
| `400` | JSON или поля не прошли проверку |
| `401` | пользователь не вошёл в систему |
| `403` | пользователь вошёл, но действие ему запрещено |
| `404` | записи с таким `id` нет |
| `409` | действие противоречит состоянию заявки |
| `500` | неожиданный сбой; клиент получает безопасное сообщение без технических подробностей |

Ошибки возвращаются в формате `ProblemDetails`.

### 2.1. Разделение `403` и `409`

`403` отвечает на вопрос «кому нельзя»: пользователь известен, но действие ему не разрешено. `409` отвечает на вопрос «в каком состоянии нельзя»: запрет следует из состояния заявки.

| Ситуация | Код | Основание |
|---|---|---|
| Специалист создаёт заявку | `403` | ФТ-11, методичка ЛР11 |
| Специалист назначает исполнителя, в том числе себя | `403` | раздел «Роли» ЛР1, методичка ЛР11 |
| Сотрудник или руководитель меняет статус | `403` | раздел «Роли» ЛР1 |
| Специалист меняет статус заявки, назначенной другому | `403` | ФТ-10, методичка ЛР11 |
| Перевод в `InProgress`, пока исполнитель не назначен | `409` | методичка ЛР8 |
| Запрещённый переход статуса | `409` | методичка ЛР8 |
| Назначение для заявки не в статусе `New` | `409` | проектное решение, см. раздел 4.4 |
| Человеческий номер оказался занят | `409` | карточка ЛР10 |

**Этапы реализации.** Этот раздел описывает итоговый контракт. Коды `401` и `403` появятся вместе со входом в ЛР11. До этого, по карточке ЛР8, пользователь определяется учебным способом, а чужой переход временно возвращает `409`.

## 3. Формат заявки в ответе

Ответы на чтение, создание и оба PATCH возвращают один и тот же объект:

```json
{
  "id": 17,
  "number": "ЗК-117",
  "title": "Закупка алюминиевого листа",
  "materialId": 2,
  "materialName": "Лист алюминиевый",
  "description": "Требуется лист для партии кастрюль на следующий месяц",
  "status": "New",
  "createdByUserId": 1,
  "assigneeUserId": null,
  "assigneeFullName": null,
  "createdAt": "2026-11-02T10:15:00Z"
}
```

`materialName` и `assigneeFullName` нужны для показа в списке (ФТ-12). Сервер получает их из связанных таблиц и в заявке не хранит.

## 4. Обязательные запросы

Пометка «проектное решение» означает, что правило предложено на этапе ЛР2 и прямо не задано в ЛР1 или методичке.

### 4.1. Список заявок

`GET /api/purchase-requests`

**Успех:** `200`. Сотрудник и руководитель получают все заявки, специалист — назначенные ему. Это проектное решение на основе ФТ-5 и истории специалиста в ЛР1: формулировка ФТ-12 («общий список» и «доступной ему заявки») допускает разное толкование.

```json
[
  {
    "id": 17,
    "number": "ЗК-117",
    "title": "Закупка алюминиевого листа",
    "materialId": 2,
    "materialName": "Лист алюминиевый",
    "description": "Требуется лист для партии кастрюль на следующий месяц",
    "status": "New",
    "createdByUserId": 1,
    "assigneeUserId": 5,
    "assigneeFullName": "Специалист по закупкам 1",
    "createdAt": "2026-11-02T10:15:00Z"
  }
]
```

Если заявок нет, ответ `200` и `[]`, а не `404`.

**Ошибки:** `401` — пользователь не вошёл.

### 4.2. Одна заявка

`GET /api/purchase-requests/{id}`

**Успех:** `200`, объект заявки из раздела 3.

**Ошибки:**

| Код | Когда |
|---|---|
| `401` | пользователь не вошёл |
| `403` | специалист запрашивает заявку, которая ему не назначена (проектное решение) |
| `404` | заявки с таким `id` нет |

```json
{
  "status": 404,
  "title": "Заявка не найдена"
}
```

### 4.3. Создание заявки

`POST /api/purchase-requests`

Разрешено роли `SupplyEmployee`.

**Запрос:**

```json
{
  "title": "Закупка алюминиевого листа",
  "materialId": 2,
  "description": "Требуется лист для партии кастрюль на следующий месяц"
}
```

**Правила полей:**

- `title`: 5–80 символов после удаления пробелов по краям;
- `materialId`: целое число больше 0; проверка, что материал существует, — проектное решение;
- `description`: 10–500 символов.

Клиент не передаёт `id`, `number`, `status`, `createdByUserId`, `assigneeUserId` и `createdAt`. Этих полей нет во входной модели, поэтому присланные значения не используются. Сервер сам задаёт `id`, `number`, `status: "New"`, создателя и время создания; исполнитель при создании пуст.

**Успех:** `201`, объект заявки из раздела 3 со `status: "New"` и `assigneeUserId: null`.

**Ошибки:**

| Код | Когда |
|---|---|
| `400` | заголовок, описание или `materialId` не прошли проверку; материала нет |
| `401` | пользователь не вошёл |
| `403` | у пользователя нет права создавать заявки (ФТ-11) |
| `409` | человеческий номер оказался занят при сохранении (карточка ЛР10) |

Пример ответа `400`:

```json
{
  "status": 400,
  "title": "Проверьте поля",
  "errors": {
    "title": ["Заголовок: от 5 до 80 символов"]
  }
}
```

### 4.4. Назначение исполнителя

`PATCH /api/purchase-requests/{id}/assignee`

Разрешено ролям `SupplyEmployee` и `SupplyManager`.

**Запрос:**

```json
{ "assigneeUserId": 5 }
```

**Успех:** `200`, объект заявки. Меняется только `assigneeUserId`; `status` остаётся `New` (ФТ-6):

```json
{
  "id": 17,
  "number": "ЗК-117",
  "title": "Закупка алюминиевого листа",
  "materialId": 2,
  "materialName": "Лист алюминиевый",
  "description": "Требуется лист для партии кастрюль на следующий месяц",
  "status": "New",
  "createdByUserId": 1,
  "assigneeUserId": 5,
  "assigneeFullName": "Специалист по закупкам 1",
  "createdAt": "2026-11-02T10:15:00Z"
}
```

**Ошибки:**

| Код | Когда |
|---|---|
| `400` | нет `assigneeUserId`; пользователь не найден или не является специалистом по закупкам (проверка пользователя и его роли — проектное решение) |
| `401` | пользователь не вошёл |
| `403` | у пользователя нет права назначать, в том числе специалист назначает себя |
| `404` | заявки с таким `id` нет |
| `409` | заявка уже не в статусе `New` (проектное решение) |

**Проектное решение.** ЛР1 описывает назначение для заявки в статусе `New`, но не говорит о других статусах и о замене исполнителя. Поэтому назначение разрешено только в `New`; пока заявка в этом статусе, повторный запрос заменяет исполнителя.

### 4.5. Изменение статуса

`PATCH /api/purchase-requests/{id}/status`

Разрешено только специалисту, назначенному на эту заявку.

**Запрос:**

```json
{ "status": "InProgress" }
```

Допустимые значения: `New`, `InProgress`, `Closed`, `Cancelled`. Перехода в `New` нет, поэтому такой запрос к существующей заявке вернёт `409`.

Разрешённые переходы:

| Из | В | Основание |
|---|---|---|
| `New` | `InProgress` | ФТ-7, критерий 3 |
| `InProgress` | `Closed` | ФТ-8 |
| `New`, `InProgress` | `Cancelled` | ФТ-9 разрешает отмену своей заявки, но не называет исходный статус; выбор двух статусов — проектное решение |

Запрет любых переходов из `Closed` и `Cancelled` — тоже проектное решение: таких переходов нет в ЛР1.

**Успех:** `200`, объект заявки с новым статусом:

```json
{
  "id": 17,
  "number": "ЗК-117",
  "title": "Закупка алюминиевого листа",
  "materialId": 2,
  "materialName": "Лист алюминиевый",
  "description": "Требуется лист для партии кастрюль на следующий месяц",
  "status": "InProgress",
  "createdByUserId": 1,
  "assigneeUserId": 5,
  "assigneeFullName": "Специалист по закупкам 1",
  "createdAt": "2026-11-02T10:15:00Z"
}
```

**Порядок проверок и ошибки:**

| Шаг | Код | Когда |
|---|---|---|
| 1 | `401` | пользователь не вошёл |
| 2 | `403` | роль пользователя не специалист по закупкам |
| 3 | `400` | значение статуса не из четырёх допустимых |
| 4 | `404` | заявки с таким `id` нет |
| 5 | `409` | исполнитель не назначен |
| 6 | `403` | заявка назначена другому специалисту (ФТ-10) |
| 7 | `409` | такой переход статуса запрещён |

Пример ответа `409`:

```json
{
  "status": 409,
  "title": "Нельзя перевести заявку в работу без исполнителя"
}
```

## 5. Вспомогательные запросы

Статус этих запросов описан в разделе 1.2.

### 5.1. Справочник материалов

`GET /api/materials`

**Успех:** `200`:

```json
[

```

### 5.2. Специалисты для назначения

`GET /api/users?role=PurchasingSpecialist`

Разрешено ролям `SupplyEmployee` и `SupplyManager`. Другие значения `role` возвращают `400`.

**Успех:** `200`:

```json
[
  { "id": 5, "fullName": "Специалист по закупкам 1" }
]
```

## 6. Ограничения контракта

- Метода `DELETE` нет: отмена заявки выполняется статусом `Cancelled`, строка остаётся в базе.
- Назначение и смена статуса — два разных запроса; общего запроса на обновление всей заявки нет.
- В адресах нет слов-действий: создание выражает метод `POST`.
