# Контракт API системы «Товароучёт»

## 1. Общие правила

Клиент Vue 3 обращается к ASP.NET Core Web API по HTTP и передаёт данные в JSON. Сервер проверяет права пользователя, входные данные и бизнес-правила, затем выполняет операции с PostgreSQL.

Базовый адрес API в учебной схеме: `http://localhost:5000`.

Главный ресурс ЛР2 — `/api/purchase-requests`. Название пути соответствует предметной области проекта и таблице заявок.

## 2. Таблица запросов

| Метод и путь | Тело запроса | Успешный ответ | Возможные ошибки |
|---|---|---|---|
| `GET /api/purchase-requests` | Нет. Возможны query-параметры фильтрации и пагинации | `200 OK`, список доступных текущему пользователю заявок. Если записей нет — `200 OK` с пустым результатом | `401`, `403` |
| `GET /api/purchase-requests/{id}` | Нет | `200 OK`, данные одной заявки | `401`, `403`, `404` |
| `POST /api/purchase-requests` | `title`, `materialId`, `description` | `201 Created`, созданная заявка с `id`, `number`, `status = New` | `400`, `401`, `403` |
| `PATCH /api/purchase-requests/{id}/assignee` | `assigneeId` | `200 OK`, обновлённая заявка; статус не меняется | `400`, `401`, `403`, `404`, `409` |
| `PATCH /api/purchase-requests/{id}/status` | `status` | `200 OK`, обновлённая заявка | `400`, `401`, `403`, `404`, `409` |

`GET` списка возвращает успешный ответ `200`, даже если подходящих записей нет. Отсутствие конкретной заявки по указанному `id` приводит к `404`.

В текущем приложении список заявок дополнительно поддерживает пагинацию и фильтры. Поэтому фактический ответ списка является объектом постраничного результата, а не обязательно простым JSON-массивом. Для требования ЛР2 важно, что пустой результат не является ошибкой `404`.

## 3. Создание заявки

### Запрос

```http
POST /api/purchase-requests
Content-Type: application/json
```

```json
{
  "title": "Закупить листовой металл",
  "materialId": 12,
  "description": "Материал необходим для выполнения производственного заказа."
}
```

При создании клиент передаёт только сведения, которые вводит пользователь или выбирает из справочника:

- `title` — заголовок от 5 до 80 символов;
- `materialId` — идентификатор существующего и неархивного материала;
- `description` — описание от 10 до 500 символов.

Клиент не передаёт `id`, `number`, `status`, `authorId` и `assigneeId`. Эти значения определяет сервер: он создаёт технический идентификатор, формирует номер `ЗК-...`, устанавливает статус `New`, записывает текущего пользователя как автора, а исполнителя оставляет пустым.

### Успешный ответ

```http
201 Created
```

Пример сокращённого тела ответа по структуре DTO проекта:

```json
{
  "id": 41,
  "number": "ЗК-0001",
  "title": "Закупить листовой металл",
  "description": "Материал необходим для выполнения производственного заказа.",
  "material": {
    "id": 12,
    "code": "М-0012",
    "article": "АРТ-12",
    "name": "Листовой металл",
    "categoryName": "Металлопрокат",
    "isArchived": false
  },
  "status": "New",
  "author": {
    "id": 3,
    "fullName": "Иванов Иван Иванович"
  },
  "assignee": null,
  "createdAt": "2026-10-01T10:00:00Z",
  "updatedAt": "2026-10-01T10:00:00Z",
  "actions": {
    "canAssign": true,
    "allowedStatuses": []
  }
}
```

Значения в примере условные и приведены для демонстрации структуры JSON.

## 4. Назначение исполнителя

### Запрос

```http
PATCH /api/purchase-requests/41/assignee
Content-Type: application/json
```

```json
{
  "assigneeId": 8
}
```

Назначить исполнителя может сотрудник отдела снабжения для собственной заявки либо руководитель отдела снабжения для доступной ему заявки. Выбранный пользователь должен быть активным специалистом по закупкам. Нельзя назначить самого себя. Назначение возможно только в статусе `New`.

### Успешный ответ

`200 OK` — возвращается обновлённая заявка. Поле `assignee` содержит назначенного специалиста. Статус остаётся `New`.

## 5. Изменение статуса

### Запрос

```http
PATCH /api/purchase-requests/41/status
Content-Type: application/json
```

```json
{
  "status": "InProgress"
}
```

Статус может менять только назначенный специалист и только для своей заявки. Для критерия ЛР1 проверяется переход `New` → `InProgress`. В дальнейшем разрешены переходы `InProgress` → `Closed` и `InProgress` → `Cancelled`.

### Успешный ответ

`200 OK` — возвращается обновлённая заявка со статусом `InProgress`.

## 6. Коды ошибок

| Код | Значение в проекте |
|---|---|
| `400 Bad Request` | Не заполнено обязательное поле, неверный формат или значение не проходит проверку |
| `401 Unauthorized` | Пользователь не вошёл в систему |
| `403 Forbidden` | Пользователь вошёл, но не имеет права выполнять действие или изменяет чужую заявку |
| `404 Not Found` | Заявка или выбранный материал не найдены |
| `409 Conflict` | Недопустимый переход статуса либо конфликт одновременного изменения заявки |

## 7. Почему назначение и статус — разные PATCH

`PATCH .../{id}/assignee` изменяет только исполнителя. `PATCH .../{id}/status` изменяет только статус. Это разные действия с разными правилами доступа: назначать может сотрудник снабжения или руководитель, а статус меняет назначенный специалист. Разделение запросов не позволяет случайно изменить оба поля одной операцией и делает критерии приёмки проверяемыми.

## 8. Соответствие методичке и текущей реализации

В контракте ЛР2 используются `PATCH` для назначения и смены статуса, как требует методичка. В приложенном исходном проекте контроллер `PurchaseRequestsController` пока объявляет эти два действия через `PUT`. Это зафиксированное различие документации и текущего кода; оно не меняет учебный контракт ЛР2. При переходе к реализации соответствующие маршруты и методы нужно будет согласовать с утверждённым контрактом.

В проекте используются названия `materialId` и `assigneeId`, а не учебные `siteId` и `assigneeUserId`, поскольку они соответствуют реальным сущностям и DTO приложения.
